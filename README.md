# Load Test Studio

Load-test **your own web application** without writing scripts. Record a real user journey in a browser, and Load Test Studio turns it into an API test. It then replays that test with hundreds or thousands of virtual users, **each logged in as a different user from your CSV file**. Load generation is spread across as many worker machines as you need, and every run ends with a **PASSED / FAILED** verdict against your performance criteria, plus HTML, JUnit and JSON reports.

| Technology | Role |
|---|---|
| **Playwright** | Records the real browser journey: every page load and API call (headers, bodies, responses, timing) |
| **TypeScript engine** | Turns the recording into a correlated API workflow and executes it: cookies, redirects, extracted tokens and IDs, assertions, think time |
| **RabbitMQ** *(distributed mode)* | Distributes the load: one durable job per virtual user, spread across workers |
| **Redis** *(distributed mode)* | Shared run state: users, live counters, latency histograms, shared login tokens, stop signals |
| **SQLite** (built into Node) | Stores tests, recordings, users files, settings and run history |

```
  Browser (Playwright)            Load Test Studio (web UI + API)                      Workers (any number, any machine)
 ┌──────────────────┐  record   ┌───────────────────────────────┐   1 job per VU    ┌─────────────┐
 │ you click through│ ────────► │ 1 Record   2 Users (CSV)      │ ───RabbitMQ─────► │ worker  ×N  │──► your application
 │ your application │           │ 3 Workflow 4 Load & criteria  │                   │ 200 VUs each│
 └──────────────────┘           │ 5 Run → live dashboard/report │ ◄───Redis──────── │ metrics     │
                                └───────────────────────────────┘  metrics, tokens  └─────────────┘
```

## Two modes

| | **In-memory** (default) | **Distributed** |
|---|---|---|
| Needs | Node.js only | + RabbitMQ and Redis |
| Load generated by | the Load Test Studio process itself | any number of worker machines (plus the app) |
| Typical capacity | up to ~1,000–3,000 VUs, depending on the machine and think time | add workers until the target system is saturated |
| Survives restarts / worker crashes | runs in progress are lost on a server restart | yes (runs resume, crashed workers' VUs move to others) |
| Select with | `LT_MODE=memory` | `LT_MODE=distributed` |

The UI, recording, workflow builder, validation, criteria, reports and CI integration are identical in both modes. Tests and run history are always stored in SQLite, so they survive restarts in either mode.

## Quick start: in-memory, nothing but Node.js

Requirements: **Node.js ≥ 22.13**.

```bash
npm install
npx playwright install chromium          # the browser used for recording
npm run build
npm start                                # → http://localhost:4100  (in-memory mode)
```

## Quick start: distributed

```bash
npm run infra:up                         # RabbitMQ + Redis in Docker (or point at your own)
LT_MODE=distributed npm start            # UI/API + an embedded worker
LT_MODE=distributed npx lt worker -c 300 # on as many machines as you need
```

> **Windows / port conflicts:** host ports are configurable, e.g.
> `RABBITMQ_UI_PORT=25672 REDIS_PORT=16379 npm run infra:up`, then start the app with `REDIS_URL=redis://localhost:16379`.

## Testing your application: the 5 steps

Open **http://localhost:4100** → **New test** → enter a name and your application's URL.

### 1. Record
Click **Start recording**. A Chromium window opens on the machine running Load Test Studio. Perform the journey the way a real user would: log in, search, add to cart, submit a form. Then close the window or click **Stop & save**. Captured requests stream into the page live.

- Only your application's traffic is kept: requests to your site's domain *and its subdomains* (e.g. `www.` and `api.`). Static assets (JS, CSS, images, fonts), analytics and RUM beacons, error reporters and chat widgets are filtered out.
- **No display on the server?** In your own browser, open DevTools → Network → *Save all as HAR*, then use **Import HAR / recording file**.

### 2. Test users
Upload a CSV (or JSON) file. The first row is the header, and every column becomes a variable, e.g. `${user.username}` and `${user.password}`.

```csv
username,password,email
qa.user001,S3cure!pass,qa.user001@yourcompany.com
qa.user002,S3cure!pass,qa.user002@yourcompany.com
```

Use dedicated test accounts that exist in the environment you are testing. Password-like columns are masked in the UI.

### 3. Workflow
Click **Build workflow**. The builder:

- **maps the values you typed** to users-file columns. **Auto-detect** finds them by matching the recording against your CSV (e.g. column `username` ← recorded `qa.user001`).
- **correlates dynamic values**: anything the server returned and the browser sent back later becomes an extracted variable. That covers JWT/bearer tokens, session and CSRF tokens (JSON, headers, cookies, hidden form fields, `<meta name="csrf-token">`), and entity IDs in URLs and bodies (`/orders/${orderId}`, `{"productId": ${productId}}`).
- **separates setup from iteration**: the login runs once per virtual user, and the business transaction repeats.
- **keeps think time** from your pauses between actions.
- assigns a variable to each host (`${baseUrl}`, `${apiUrl}`, …) so the test can be pointed at another environment.

Then review it in the step editor. For each step you can edit the URL, headers and body, and add **assertions** (expected status codes, text the response body must contain). You can add **extractors** (JSON path, header, cookie or regex), reorder or delete steps, and move steps between setup and iteration. **Edit JSON** gives full control.

**Validate** runs the workflow once as one user and shows every request, its status, timing and the values extracted from it. Fix any red step here before loading the system.

### 4. Load & pass/fail criteria
- **Virtual users (threads)**, **ramp-up**, and a stop condition: **duration** or **iterations per user**.
- **How virtual users pick test users**: one user each (wraps round the list), strictly unique, or a new user every iteration.
- **Think-time multiplier**: 1 = realistic pacing, 0 = maximum pressure. **Request timeout**.
- **Environment**: override `${baseUrl}` and any other recorded host to run the same test against staging, pre-prod and so on. Extra variables are also available here.
- **Pass/fail criteria** (SLAs), on all requests or on a specific step: p50/p90/p95/p99/avg/max response time, error rate, throughput. For example: *p95 < 800 ms*, *error rate < 1 %*, *[POST /api/checkout] p99 < 2000 ms*.

### 5. Run & reports
**Start load test** opens the live dashboard: active VUs, throughput, error rate, p95, the criteria evaluated live, charts over time, per-step response times and grouped errors. You can **Stop** at any time and keep the results collected so far.

When the run finishes it gets a **PASSED / FAILED** verdict and becomes a permanent report with **HTML**, **JUnit XML** and **JSON** downloads. **Run history** lists every run across all tests.

## CI/CD integration

Create the test once in the UI, then run it from any pipeline. The command exits **0 = passed, 1 = failed, 2 = error**:

```bash
npx lt ci <testId> --server https://loadtest.internal:4100 --token $LT_API_TOKEN \
  --junit reports/junit.xml --html reports/load-test.html \
  [--vus 200] [--duration 300] [--base-url https://staging.example.com]
```

`<testId>` is the id in the test's URL (`/tests/<testId>/…`). Publish the JUnit file with your CI's test-report step (Jenkins, GitLab, Azure DevOps and GitHub Actions all support it).

Or call the REST API directly: `POST /api/tests/:id/runs` → poll `GET /api/runs/:runId` → `GET /api/runs/:runId/junit.xml`.

## Scaling out (distributed mode)

In-memory mode runs every virtual user inside the server process. Raise `LT_EMBEDDED_WORKER_CONCURRENCY` (default 1000) for more, until that machine's CPU or network is the limit. Beyond that, switch to `LT_MODE=distributed`.

Workers are stateless load generators. Run as many as you need on any machine that can reach RabbitMQ, Redis **and your application**:

```bash
# Node
AMQP_URL=amqp://user:pass@mq-host:5672 REDIS_URL=redis://redis-host:6379 npx lt worker --concurrency 300

# Docker (on the same host as docker compose)
docker compose up -d --scale worker=10
```

**Workers & system** in the UI shows every worker, its load and the total capacity. A test with more VUs than the total capacity triggers a warning, because the extra VUs would wait in the queue.

**Resilience** (distributed mode)
- A virtual user's job is acknowledged only when it finishes. If a worker crashes, RabbitMQ hands its VUs to other workers and the run still completes.
- Stopping a worker gracefully (Ctrl+C / SIGTERM) returns its VUs to the queue.
- Workers reconnect automatically after broker or Redis outages.
- Runs survive a restart of the web server, because their state lives in Redis and monitoring resumes.
- If the target stops responding, VUs back off after failed iterations instead of hammering it in a tight loop.

## Production deployment

```bash
cp .env.example .env        # set LT_AUTH_USER / LT_AUTH_PASSWORD / LT_API_TOKEN, RabbitMQ credentials

# distributed: RabbitMQ + Redis + app + workers
docker compose up -d --build --scale worker=4

# or in-memory: a single container, no RabbitMQ/Redis
docker build -t load-test-studio . && docker run -d -p 4100:4100 -v lt-data:/data -e LT_AUTH_USER=admin -e LT_AUTH_PASSWORD=change-me load-test-studio
```

This starts RabbitMQ, Redis, the app (UI + API on `:4100`, data in the `app-data` volume) and the workers. In containers, live recording is disabled because there is no display, so import HAR files instead. Alternatively, run the app natively on a desktop machine to record, pointing it at the same RabbitMQ and Redis.

Security:
- Set `LT_AUTH_USER` / `LT_AUTH_PASSWORD` (HTTP basic auth for UI and API) and `LT_API_TOKEN` (bearer token for CI) whenever the app is reachable by others. The server warns at startup if it listens on the network without authentication.
- Put it behind HTTPS (reverse proxy).
- Change the default RabbitMQ credentials.
- Users files are stored in the app database. Use test accounts only.

**Only load-test systems you own or are authorized to test.**

### Configuration

| Variable | Default | |
|---|---|---|
| `LT_MODE` | `memory` | `memory` (single process) or `distributed` (RabbitMQ + Redis + workers) |
| `HOST` / `PORT` | `127.0.0.1` / `4100` | UI/API bind address |
| `LT_DATA_DIR` | `.data` | SQLite database location |
| `LT_AUTH_USER`, `LT_AUTH_PASSWORD` | — | basic auth (disabled when empty) |
| `LT_API_TOKEN` | — | bearer token for CI/API |
| `AMQP_URL` | `amqp://guest:guest@localhost:5672` | RabbitMQ (distributed) |
| `REDIS_URL` | `redis://localhost:6379` | Redis (distributed) |
| `LT_EMBEDDED_WORKER` | `true` | distributed: also generate load from the app process (always on in memory mode) |
| `LT_EMBEDDED_WORKER_CONCURRENCY` | `1000` memory / `100` distributed | max VUs generated by the app process |
| `LT_CONCURRENCY` | `200` | max VUs per standalone worker |
| `LT_RECORDER_ENABLED` / `LT_RECORDER_HEADLESS` | `true` / `false` | live browser recording |
| `LT_REDIS_RUN_TTL_SEC` | `86400` | how long raw run data stays in Redis/memory after results are saved |
| `LT_MAX_UPLOAD_MB` | `50` | max users/HAR upload size |
| `LT_JOB_QUEUE` | `lt.vu.jobs` | RabbitMQ queue name |

RabbitMQ's `consumer_timeout` must exceed your longest test, because a VU's job stays unacknowledged while it runs. [docker/rabbitmq.conf](docker/rabbitmq.conf) sets 24 h. Apply the same setting to an external broker.

## Command line (optional)

Everything in the UI is also available as a CLI for scripting:

```bash
npx lt record https://your.app -u username=qa.user001 -u "password=S3cure!pass" -o rec.json
npx lt build rec.json -o workflow.json            # or a .har file
npx lt validate workflow.json --users users.csv
npx lt run workflow.json --users users.csv --vus 100 --ramp-up 30 --duration 300 --local   # in-process, no infra
npx lt run workflow.json --users users.csv --vus 2000 --duration 600 --distributed         # RabbitMQ + Redis + workers
npx lt worker -c 200 | lt status | lt stop <runId> | lt report <runId>                     # distributed mode
```

`lt record --script flow.js --headless` replays a Playwright script instead of manual clicking. The script is a module exporting `default async (page, userFields) => {}`. This is useful for re-recording automatically.

## Good to know

- **What is simulated:** the HTTP traffic of the journey (pages and API calls), with per-user cookies, tokens and think time. The load generator does not execute JavaScript or render pages, so it measures server and API performance rather than browser rendering. This is the standard protocol-level approach.
- **Correlation is heuristic.** Always **Validate** after building. If a step fails with 401/403/404, look for a value that is still hard-coded and add an extractor for it.
- **Session-cookie logins** must not use the shared login cache (the cookie is not shared). Token-based logins can.
- Response times are recorded in log-scale buckets (±2.5 %), which lets percentiles merge exactly across workers.

```
src/
  server/            web API (Fastify), SQLite store, run & recording services, live events (SSE)
  recorder/          Playwright recording session, HAR import
  builder/           recording → workflow: filtering, parameterization, correlation, think time
  engine/            virtual user: templating, cookie jar, redirects, extractors, assertions
  backend/           job queue + run state: in-memory, or RabbitMQ + Redis (same interfaces)
  distributed/       controller (launch/monitor) and worker (runs virtual users), backend-agnostic
  metrics/           collector, histogram, stats, thresholds/verdict, JUnit and HTML reports
  cli.ts             lt command
web/src/             React UI
test/                unit tests
```
